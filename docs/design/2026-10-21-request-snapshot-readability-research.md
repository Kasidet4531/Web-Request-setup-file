# งานวิจัยประกอบการปรับความอ่านง่ายของ Request Snapshot

วันที่ค้นคว้า: 21 ตุลาคม 2026 (Asia/Bangkok)

สถานะ: ข้อมูลประกอบการตัดสินใจ ยังไม่ใช่แบบที่ผู้ใช้อนุมัติหรือข้อกำหนดให้ลงมือพัฒนา รายงานนี้ตรวจเอกสารและ source code ไม่ได้เปิดแอป ประเมินหน้าจอจริง หรือทดสอบกับผู้ใช้

## คำตอบและขอบเขต

**ควรศึกษาทั้งแนวปฏิบัติและงานวิจัยก่อนออกแบบใหม่** โดยใช้มาตรฐาน accessibility เป็นเงื่อนไขพื้นฐาน ใช้ design system เป็นตัวอย่างวิธีจัดข้อมูล และใช้งานทดลองช่วยตั้งสมมติฐาน จากนั้นจึงประเมินต้นแบบด้วยงานอ่านที่ตรงกับระบบนี้ หลักฐานที่พบยังไม่เพียงพอจะสรุปว่า layout แบบใดดีที่สุดสำหรับ Request Snapshot

เป้าหมายที่ผู้ใช้ยืนยันคือ **อ่านฟอร์มทั้งชุดตามสภาพทันทีหลัง Audit History entry ที่เลือก** ได้แก่ Requester Information, PSF Created Information และ Work Status ภายใต้สิทธิ์การมองเห็นเดิม ไม่ได้ยืนยันว่าการดูเฉพาะความเปลี่ยนแปลงเป็นงานหลัก และยังไม่ได้ตกลงให้ซ่อนค่า `Previous` ดังนั้นข้อเสนอด้านล่างไม่มีข้อสรุปให้แสดงเฉพาะ changed fields หรือยุบค่าเดิมโดยอัตโนมัติ เป้าหมายนี้สอดคล้องกับนิยาม [Request Snapshot ใน CONTEXT.md](../../CONTEXT.md) และ [ADR 0016](../adr/0016-full-request-snapshot-per-audit-history-entry.md)

อ่าน [รายงาน form UX วันที่ 20 ตุลาคม](2026-10-20-form-ux-accessibility-research.md) เป็นจุดเริ่มค้นคว้าเท่านั้น รายงานเดิมมีคำเตือนเรื่อง citation และเนื้อหาส่วนมากเกี่ยวกับการกรอกข้อมูล จึงไม่ยกข้อเสนอเรื่อง label อยู่ด้านบน, multi-step form หรือ progressive disclosure มาเป็นหลักฐานว่าช่วยการอ่าน Request Snapshot

## หลักฐานภายนอกที่ตรวจจากต้นฉบับ

ใช้แหล่งปฐมภูมิ 6 รายการ แยกประเภทเพื่อไม่ให้น้ำหนักคำแนะนำจากผลิตภัณฑ์เท่ากับผลการทดลอง หรือเรียกข้อเสนอด้านภาพว่าเป็นข้อบังคับของ WCAG

### 1. มาตรฐาน: WCAG 2.2

[W3C Recommendation: WCAG 2.2](https://www.w3.org/TR/WCAG22/) เป็นมาตรฐานที่มี success criteria ตรวจประเมินได้ ประเด็นตรงกับการอ่านหน้านี้ ได้แก่

- [1.3.1 และ 1.3.2 ระดับ A](https://www.w3.org/TR/WCAG22/#info-and-relationships): ความสัมพันธ์ชื่อ–ค่าและลำดับการอ่านที่มีผลต่อความหมายต้องเข้าถึงได้ด้วยโปรแกรม ไม่ควรฝากความหมายไว้กับตำแหน่งที่มองเห็นเพียงอย่างเดียว
- [1.4.1 ระดับ A](https://www.w3.org/TR/WCAG22/#use-of-color): ใช้สีเป็นวิธีเดียวในการสื่อข้อมูลไม่ได้ จึงต้องมีข้อความที่แยกค่าก่อนหน้า/ค่าหลัง entry แม้จะมีแถบสีอยู่แล้ว
- [1.4.3 ระดับ AA](https://www.w3.org/TR/WCAG22/#contrast-minimum): ข้อความปกติมี contrast อย่างน้อย 4.5:1; large text อย่างน้อย 3:1 ข้อมูล read-only ที่ต้องอ่านไม่ได้กลายเป็น inactive control เพียงเพราะแก้ไขไม่ได้ ค่า `Previous` ก็เป็นเนื้อหาที่ต้องอ่าน
- [1.4.4 และ 1.4.10 ระดับ AA](https://www.w3.org/TR/WCAG22/#resize-text): รองรับการขยายข้อความ 200% และ reflow ที่ความกว้างเทียบเท่า 320 CSS pixels โดยไม่สูญเสียข้อมูลหรือการทำงาน และไม่ต้องเลื่อนสองทิศทาง ยกเว้นเนื้อหาที่จำเป็นต้องมี layout สองมิติ
- [1.4.12 ระดับ AA](https://www.w3.org/TR/WCAG22/#text-spacing): การปรับ text spacing ตามเกณฑ์ต้องไม่ทำให้เนื้อหาหรือการทำงานสูญหาย เกณฑ์นี้ไม่ได้บังคับว่าค่าเริ่มต้นของทุกหน้าต้องใช้ spacing เหล่านั้น
- [2.4.6 ระดับ AA](https://www.w3.org/TR/WCAG22/#headings-and-labels): headings และ labels ต้องบอกหัวข้อหรือวัตถุประสงค์ได้

การใช้กับงานนี้: เป็นเงื่อนไขสำหรับต้นแบบและการพัฒนา ไม่ใช่หลักฐานว่า layout ใหม่จะอ่านเร็วขึ้น WCAG ข้างต้นไม่ได้กำหนด font ขั้นต่ำเป็นจำนวน px; การพบข้อความ 12px จึงยังไม่ใช่หลักฐานว่าผิด WCAG ต้องตรวจความคมชัด การขยาย และการอ่านจริงด้วย

### 2. คำแนะนำ accessibility: WAI Page Structure — Headings

[W3C WAI: Headings](https://www.w3.org/WAI/tutorials/page-structure/headings/) อธิบายว่า heading สื่อโครงสร้างเนื้อหา และ browser/assistive technology สามารถใช้ช่วยนำทางภายในหน้าได้ แนะนำให้เรียงระดับ heading ตามโครงสร้าง และเชื่อม heading กับ region ที่เกี่ยวข้อง

การใช้กับงานนี้: ให้ Requester Information, PSF Created Information และกลุ่มย่อยมีลำดับและชื่อชัดเจน เพื่อช่วยทั้งการอ่านต่อเนื่องและการกลับมายังส่วนเดิม ข้อแนะนำนี้สนับสนุนโครงสร้างเชิงความหมาย ไม่ได้พิสูจน์ว่าต้องใช้สารบัญติดขอบจอหรือ card จำนวนหนึ่ง หน้า WAI นี้ระบุเองว่าเป็น best-practice tutorial และรวมเกณฑ์จากหลายระดับ จึงไม่ถือว่าทุกคำแนะนำเป็นข้อบังคับระดับ AA

### 3. แนวปฏิบัติสำหรับชื่อ–ค่า: GOV.UK Summary list

[GOV.UK Design System: Summary list](https://design-system.service.gov.uk/components/summary-list/) ใช้รายการ key/value สำหรับข้อมูล เช่น คำตอบที่ผู้ใช้ให้ไว้ หรือ metadata แต่ละแถวมีชื่อและค่า มีตัวอย่างแบบไม่มี action และแนะนำให้ใช้ heading เพิ่มโครงสร้างเมื่อมีหลายรายการ ใช้ `<dl>` สำหรับชื่อ–ค่า และแยกกรณีข้อมูลตารางหรือรายการธรรมดาออกไป

การใช้กับงานนี้: เป็นตัวอย่างที่ใกล้งานอ่านค่าฟอร์มมากกว่าคำแนะนำเรื่อง data entry คำว่า summary list ไม่ได้เป็นเหตุผลให้ตัดค่าที่ไม่เปลี่ยนออกจาก Request Snapshot อาจนำหลักการจับคู่ชื่อ–ค่าและการแบ่งส่วนมาพิจารณา โดยยังแสดงข้อมูลครบตามงานที่ยืนยัน

ข้อจำกัด: นี่เป็นแนวปฏิบัติจากผู้ดูแล design system ไม่ใช่ผลทดลองเปรียบเทียบ Request Snapshot และไม่ได้พิสูจน์ว่าต้องเปลี่ยน `<output>` ปัจจุบันเป็น `<dl>` หรือย้าย label ไปอยู่เหนือค่าบน desktop จึงควรประเมินความหมายและการใช้งานกับ assistive technology ก่อนตัดสินใจ

### 4. ตัวอย่างการวางบริบทอดีต: Confluence

[Atlassian: Page History and Page Comparison Views](https://confluence.atlassian.com/doc/page-history-and-page-comparison-views-139379.html) อธิบายการเปิดเนื้อหาของหน้ารุ่นเก่าพร้อม header และการนำทางไป current version, page history และรุ่นก่อนหน้า/ถัดไป โดยมี Compare with Current เป็นอีกการทำงานหนึ่ง

การใช้กับงานนี้: เป็นตัวอย่างให้พิจารณาการบอกว่า “กำลังอ่านเนื้อหาของเวลาใด” และทางกลับไปข้อมูลปัจจุบัน/History อย่างชัดเจน การอ่านเนื้อหาอดีตทั้งชุดสามารถมีอยู่พร้อมทางไปดูการเปรียบเทียบได้

ข้อจำกัด: เอกสารผลิตภัณฑ์อธิบายพฤติกรรม ไม่รายงานผลทดลองด้านความอ่านง่าย และเนื้อหาเอกสารต่างจากฟอร์ม PSF Request จึงไม่มีเหตุผลให้คัดลอกหน้าตาหรือเพิ่มความสามารถ restore ของผลิตภัณฑ์นั้นในงานนี้

### 5. งานทดลองเรื่องกลุ่มและหัวข้อ: Hornof (2001)

Anthony J. Hornof, *Visual Search and Mouse-Pointing in Labeled versus Unlabeled Two-Dimensional Visual Hierarchies*, ACM TOCHI 8(3), 171–197: [บทความฉบับเต็มที่เว็บไซต์ผู้วิจัย](https://ix.cs.uoregon.edu/~hornof/downloads/ToCHI_2001.pdf) โดยเฉพาะ Methods §7 และ Results §8

- วิธีศึกษา: ผู้เข้าร่วม 16 คน ค้นหาและคลิกชุดตัวอักษร consonant–vowel–consonant ที่จัดเป็นกลุ่ม เปรียบเทียบกลุ่มมี/ไม่มี heading โดยบอก target และ label ของกลุ่มล่วงหน้าในเงื่อนไขมี heading; label เป็นตัวเลข และสิ่งเร้าถูกออกแบบเพื่อตัดปัญหาความหมายของคำออก
- ผล: กลุ่มมี heading ใช้เวลาค้นหาสั้นกว่าอย่างมีนัยสำคัญ ในกรณีหกกลุ่ม ค่าเฉลี่ย search time คือ 1,740 ms เมื่อมี heading เทียบกับ 3,090 ms เมื่อไม่มี (Table I) ผลนี้เป็นของเงื่อนไขทดลอง ไม่ใช่ค่าคาดการณ์สำหรับแอป
- การใช้กับงานนี้: สนับสนุนให้ตั้งสมมติฐานว่าโครงสร้างและหัวข้อกลุ่มที่ผู้อ่านเข้าใจอาจช่วยหาตำแหน่งข้อมูล แล้วตรวจด้วยศัพท์และกลุ่มจริงของ PSF Request
- ข้อจำกัด: เป็นงานหาเป้าหมายบนหน้าจอขนาดเล็ก มี cue และสิ่งเร้าเทียม ไม่ใช่การอ่านฟอร์มยาวจนจบ ไม่มี previous/current values และไม่ได้ทดสอบผู้ใช้ที่มีความบกพร่องทางสายตาหรือการเคลื่อนไหว จึงไม่ยืนยันผลด้านความเข้าใจทั้งฟอร์ม จำนวนกลุ่มที่เหมาะสม หรือความจำเป็นในการเปลี่ยนลำดับ Form Schema

### 6. งานทดลองเรื่องการอ่านและความกว้าง: Dyson & Kipping (1998)

Mary C. Dyson และ Gary J. Kipping, *The Effects of Line Length and Method of Movement on Patterns of Reading from Screen*, Visible Language 32(2), 150–181: [หน้าบทความจากวารสาร](https://journals.uc.edu/index.php/vl/article/view/5671) และ [ฉบับเต็ม](https://journals.uc.edu/index.php/vl/article/download/5671/4535/7348) โดยเฉพาะ Methods, Results และ Discussion ของการทดลองทั้งสอง

- วิธีศึกษา: อ่านข้อความร้อยแก้วภาษาอังกฤษบนหน้าจอ วัดเวลา ความเข้าใจ และการตัดสินว่าอ่านง่าย การทดลองแรกมี 48 คน แบ่ง scrolling/paging กลุ่มละ 24 คน และเปลี่ยนความยาวบรรทัด 25–100 characters; การทดลองถัดมามี 24 คน เปลี่ยนทั้งวิธีเลื่อนและความยาวบรรทัด พร้อมปรับพื้นหลัง
- ผล: การทดลองแรกพบว่า 100 characters อ่านได้เร็วกว่า 25 characters แต่ผู้เข้าร่วมตัดสินว่า 55 characters อ่านง่ายกว่า; ไม่พบความแตกต่างด้านความเข้าใจอย่างมีนัยสำคัญ การทดลองถัดมาไม่พบความแตกต่างของความยาวบรรทัดในเงื่อนไข paging และผลด้านเวลา scrolling เกี่ยวข้องกับเวลาเลื่อนด้วย จึงไม่ควรย่อผลเป็น “บรรทัดยาว/สั้นดีกว่าเสมอ”
- การใช้กับงานนี้: แยกการประเมิน “รู้สึกอ่านง่าย” ออกจาก “อ่านค่าถูก เข้าใจถูก และใช้เวลาเท่าใด” โดยเฉพาะ field ที่มีข้อความหลายบรรทัด
- ข้อจำกัด: เป็น prose reading ด้วยเทคโนโลยีหน้าจอและการเลื่อนของยุค 1990 ไม่ใช่คู่ชื่อ–ค่าของฟอร์ม ไม่ใช่ภาษาไทย และไม่มี historical context ผลนี้ไม่กำหนดความกว้าง 840px, label column, font หรือจำนวนอักขระที่เหมาะสมสำหรับระบบปัจจุบัน

## หลักการที่ควรนำไปสร้างสมมติฐานของต้นแบบ

ข้อเสนอต่อไปนี้เป็นสิ่งให้เปรียบเทียบและประเมิน ยังไม่มีข้อใดเป็นแบบที่อนุมัติแล้ว

| ประเด็น | สมมติฐาน/ทางเลือกที่ควรพิจารณา | ฐานและขอบเขต |
| --- | --- | --- |
| ความครบของข้อมูล | อ่านค่าหลัง entry ได้ต่อเนื่องทั้งสองฟอร์มและ Work Status; ตรวจ inventory ของ metadata, ค่าว่าง, ค่าหลายบรรทัด และ field ที่ถูกถอดออก | เป้าหมายผู้ใช้และ domain ของระบบเป็นฐาน ส่วนรูปแบบแสดงต้องประเมินอีกครั้ง |
| ชื่อ–ค่า | ให้ผู้อ่านจับคู่ label กับค่าที่ถูกต้องได้ในแถวยาวและเมื่อขยายหน้าจอ; เปรียบเทียบ spacing/น้ำหนักข้อความโดยไม่เปลี่ยนเนื้อหา | GOV.UK และ WCAG สนับสนุนความสัมพันธ์ชื่อ–ค่า แต่ยังไม่เลือกสองคอลัมน์หรือ label เหนือค่า |
| กลุ่มและลำดับ | ทำให้หัวข้อส่วนหลักกับหัวข้อ Form Schema แยกแยะได้ รักษาลำดับที่ผู้ใช้คุ้นเคยระหว่างประเมิน; พิจารณาทางข้ามไปส่วนต่าง ๆ หากงานจริงต้องย้อนกลับบ่อย | WAI + Hornof สนับสนุนเหตุผลของหัวข้อ; ประโยชน์ของสารบัญหรือรูปแบบ sticky ยังไม่ยืนยัน |
| เวลาและสถานะของหน้า | บอกให้ชัดว่าเป็นค่าทันทีหลัง entry ใด วันเวลา/เขตเวลาใด และทางกลับไป History หรือข้อมูลปัจจุบันหมายถึงอะไร | นิยาม Request Snapshot + ตัวอย่าง Confluence; ยังไม่มีผลทดลองในผู้ใช้ระบบนี้ |
| ค่าใน snapshot กับค่าเดิม | ค่าหลัง entry เป็นค่าที่อ่านตอบงานหลักได้ชัด; ค่าเดิมมีข้อความบอกช่วงเวลาและจับคู่กับ field เดียวกันได้ ไม่พึ่งสีเพียงอย่างเดียว ประเมินรูปแบบที่ยังเห็นค่าเดิมได้ก่อนเปลี่ยนการเปิด/ปิด | WCAG เป็นฐานเรื่องความหมายและสี; ตำแหน่ง น้ำหนัก และความหนาแน่นเป็นสมมติฐาน ยังไม่มีการอนุมัติให้ซ่อน `Previous` |
| ความยาวและการขยาย | รักษาเนื้อหาเต็มและ newline โดยไม่ตัดข้อความสำคัญ ให้ reflow และ user text spacing ทำงานได้; ประเมินด้วย field ยาวจริง | WCAG เป็นเกณฑ์ accessibility; Dyson & Kipping เตือนว่า preference กับ performance อาจต่างกัน ไม่ได้ให้สูตร pixel ที่เหมาะสม |

ไม่พบการศึกษาปฐมภูมิที่ทดสอบ **การอ่านฟอร์มทั้งชุด ณ entry ย้อนหลัง พร้อมค่าก่อนหน้า** โดยตรงในชุดการค้นคว้านี้ การย้าย/ยุบค่าเดิม การทำ sidebar หรือการเปลี่ยนเป็น card จึงยังไม่มีหลักฐานตรงมารองรับ ข้อจำกัดนี้ไม่ใช่ข้อพิสูจน์ว่าไม่มีงานวิจัยดังกล่าวอยู่ที่อื่น

## คำถามที่ยังต้องทราบก่อนเลือกแบบ

- “อ่านทั้งฟอร์ม” ในงานจริงนำไปใช้ตัดสินใจอะไร และข้อมูลใดต้องเชื่อมข้าม Requester Information กับ PSF Created Information?
- อ่านไล่ตั้งแต่ต้นบ่อยเพียงใด เทียบกับกลับมาหาค่าที่จำตำแหน่งได้ และต้องอ่าน `Previous` ระหว่างทางบ่อยเพียงใด?
- กลุ่ม/ลำดับของ Form Schema ปัจจุบันช่วยงานอ่านแล้วหรือมีจุดที่ต้องการเปลี่ยน รวมถึง metadata ที่ต้องเห็นในมุมมองอดีต?
- จอ ความละเอียด ระดับ zoom และความยาวข้อมูลที่ใช้จริงเป็นอย่างไร; มีการคัดลอกค่า พิมพ์ หรือใช้ screen reader ระหว่างงานหรือไม่?

คำถามเหล่านี้ช่วยเลือกระหว่างต้นแบบ ยังไม่จำเป็นต้องตั้งคำถามใหม่ว่าเป้าหมายหลักคือดู diff หรืออ่านทั้งฟอร์ม เพราะผู้ใช้ยืนยันงานหลักแล้ว

## งานประเมินต้นแบบในขั้นถัดไป

เป็นข้อเสนอสถานการณ์ ไม่ใช่ผลทดสอบหรือแผนที่ดำเนินการแล้ว ควรใช้ข้อมูลตัวอย่างชุดเดียวกันระหว่างแบบ และตกลงเกณฑ์ยอมรับก่อนประเมิน

1. เปิด entry ที่กำหนด อ่านฟอร์มทั้งชุด แล้วอธิบายสภาพ PSF Request ขณะนั้น โดยตอบคำถามที่ต้องใช้ทั้งค่าที่เปลี่ยนและค่าที่ไม่เปลี่ยน วัดความถูกต้องและ field ที่ตกหล่น ควบคู่กับเวลาและความรู้สึกว่าอ่านง่าย
2. ให้ field หนึ่งมีค่าก่อนหน้า/หลัง entry/ปัจจุบันต่างกัน แล้วขอค่าที่ใช้ ณ entry นั้น รวมถึงค่าเดิมและ Work Status ตรวจว่าผู้อ่านสลับช่วงเวลาหรือไม่ โดยไม่ชี้ตำแหน่งคำตอบให้
3. อ่านค่าหลายบรรทัด ค่าที่เว้นว่าง และ Removed fields แล้วอธิบายว่าข้อมูลใดอยู่ในฟอร์ม ณ ตอนนั้น ข้อมูลใดเป็นบริบทก่อนหน้า และส่วนใดถูกจำกัดตามสิทธิ์
4. หลังอ่านถึงท้ายฟอร์ม ให้กลับมาหาส่วนที่เกี่ยวข้องกับคำถามอีกครั้ง ตรวจการหาตำแหน่งและความเข้าใจหัวข้อ พร้อมตรวจลำดับอ่าน/การนำทางด้วย keyboard และ screen reader ตามวิธีที่ผู้เข้าร่วมใช้
5. ประเมินการอ่านชื่อ–ค่าชุดเดิมเมื่อขยายข้อความ 200%, ที่ reflow เทียบเท่า 320 CSS pixels และเมื่อปรับ text spacing ตรวจการตัด/ซ้อน/หายของข้อความและบริบทช่วงเวลา ทั้ง light และ dark theme ที่รองรับ

ความสำเร็จที่ควรมุ่งตรวจคืออ่านข้อมูลครบ ตอบค่าของเวลาที่เลือกถูก และกลับหาตำแหน่งได้ การผ่าน accessibility กับความชอบด้านภาพควรมีหลักฐานของตนเอง ไม่ใช้แทนความถูกต้องของงานอ่าน
